# 仓库设计文档

> 所属插件：H3RndNew（热血插件）。功能名统一为「仓库」。
> 状态：2026-10-12 设计稿，静态调研与离线格式探针已完成，未实现、未进行游戏内验收。
> 基线：本机 SoD / HD_SOD。逆向证据见 [背包逆向笔记](<../../H3Note/英雄宝物背包容量与自动整理逆向笔记.md>) 与 [游戏本体存档读档核心逆向笔记](<../../H3Note/游戏本体存档读档核心逆向笔记.md>)。H3SaveLoadEnhance 是界面增强插件，不是本功能的存档核心依赖。

## 1. 已确定需求

1. 每个英雄都有独立仓库，按游戏预定义的固定英雄 ID 对应。本机 SoD 为 156 个英雄，ID 为 0..155；未出场英雄也有空仓库。
2. 仓库没有类似随身背包 64 格的玩法容量上限；使用动态容器，列表按可见区域分页/滚动。实际内存、文件与整数表示能力不是数学意义的无限，分配失败时拒绝操作并保留源物品，不静默丢弃。
3. 只在 HD_SOD 的完整背包弹窗出现时同时显示仓库；背包关闭、重开或异常退出时仓库同步退出。普通英雄页、原版五格栏、换装选择器、战斗和 F11 设置窗均不单独弹仓库。
4. 背包面板增加「一键移入仓库」按钮；另支持先点击一件背包物品，再点击仓库区域移入这一件。
5. 仓库面板提供「一键取到背包」按钮，最多取到原背包可容纳的数量；取不下或无法合法加入的物品留在仓库。
6. 保存整局所有英雄的仓库到**游戏本体存档文件**，不另建战场档、跨存档公用库或正式 sidecar 数据文件。
7. 存档扩展采用用户指定时序：原版完成存档并关闭文件后追加仓库块；读档先让原版完成，成功后再读仓库块。不得把仓库内容塞入英雄固定 64 格数组或扩大英雄结构。
8. 本文仅设计 H3RndNew 的后续功能，不改变当前 RNG、宝屋最大化功能，不自动提版本，不修改出厂配置或部署游戏。

## 2. 结论与实施门槛

**库存与 UI 结构可行；后置附件追加有独立codec探针，但游戏实际是否容忍附件尾部仍须验收。尚不能称整个方案已实机可行。**

- 原生英雄池固定，插件可在自身运行内存按英雄 ID 持有独立库存。
- HD 完整背包已有全屏事件容器，可在其中加入并列仓库视觉面板，而不是新建第二个模态列表。
- 原版SaveGame在返回前已关闭其流；SaveGame后置hook因此能在原操作之后追加，不需要改写原生压缩流。
- 原生读取按序列化字段请求数据，gzip读取器在单个压缩成员结束后会尝试解析后续成员头，签名不符时进入transparent处理分支；关闭读流只释放inflate状态与文件，不强制把物理输入耗尽。这为末尾附件提供静态支持，但不能保证所有HD/SoD_SP路径都接受它，仍须用真实存档副本游戏内验收。
- 离线内存探针对五份GM1验证了附件编码/解析、原前缀不变与损坏拒绝，共42项通过。没有修改真实存档，也没有执行游戏内读档。

**第一阶段先做真实存档副本的尾随附件读档验证。** 如果目标HD/SoD_SP链路不能接受，应先停止并报告证据，再与用户确认路径；不得擅自改成独立sidecar、覆盖英雄结构或挪用SoD_SP私有记录。

## 3. 身份与局内模型

```text
WarehouseState
  sessionGeneration             // 本进程当前局，非库存主键
  mutationEpoch                 // 改动后递增，消除旧选择
  hero[156]
    heroId                      // 固定0..155
    records: vector<ArtifactRecord>

ArtifactRecord
  artifactId: int32
  subtype: int32                // 卷轴法术等完整第二字段
```

- 8 字节记录完整保存，不按 ID 去重，不合并相同宝物，不能只保留名称/图标/第一 DWORD。
- 库存键不是 `hero*`、当前玩家、左右位置、英雄名、头像或所属队伍。英雄指针只用于当前事务，须与 `hero.id` 和池槽一致。
- 原生 `GetHero(0x4317D0)` 为 `Main+0x21620+id*0x492`；`hero.id` 位于 `+0x1A`。在读写插件数据之前显式判 `0<=id<156`，因为原生 GetHero 不提供充分上界保护。
- 英雄易主、解雇、战败、重新招募不自动清仓，库存仍归同一英雄 ID；这是“每个固定英雄独立仓库”的默认设计。不会自动转给击败者，不伪装成原生战利品或装备效果。
- 仓库中物品不被原版的任务交付、持有检测、组合、商店、祭坛、AI 搜索自动看到；使用前需取回背包。不是透明无限背包。
- 新局/新地图需要空状态；同一地图不同存档各自恢复各自 snapshot，不通过地图名共享库存。战役地图迁移、联机与英雄扩展 MOD 需另行验证，未验收时不能宣称支持。

## 4. 复用 HD 窗口

### 4.1 已核接入点

本机 HD_SOD SHA256：`37FA9723F39349558CA82F5379531311C266E8DFFFA382F80BB7550902039C75`。以下 preferred VA 仅用于核查；运行时必须用实际模块基址 + RVA，并校验目标指令。

| 项 | 核查结果 |
| --- | --- |
| 完整弹窗 | RVA `0x39A00`，末尾 `ret 0x18`，六个栈参数、callee-clean/stdcall 形态 |
| 参数 | x、y、hero、当前未读的保留标记、画阴影开关、跨英雄点击权限 override；不能按旧的 cdecl 四参注册 |
| 实例 | factory RVA `0xFB180` 创建全屏事件容器；405×459 是内部背包视觉区 |
| 对象字段 | `+0x70` callback，`+0x74` 状态栏，`+0x78` hero，`+0x7C` 返回选择，`+0x80` override；不借用 `+0x98` 最新控件临时字段存业务数据 |
| 原格子 | 热区 `1000+i`，图标 `2000+i`，i=0..63；热区47×47，坐标步长46，图标44×44 |
| 模态前 | RVA `0x39E66` 起准备运行，`0x39E7B` 调 `ShowAndRun`；候选接入点需核覆盖完整指令、寄存器与重入 |
| 生命周期 | 模态返回后读取结果，RVA `0x39EB8` 析构并释放对象；函数返回后不能再借用背包实例 |
| 原回调 | RVA `0x395D0`，stdcall(dialog,msg)，`ret 8`；左键下选格后 EndDialog，外层 caller 再执行真正拿取 |

### 4.2 展示与生命周期

- 原背包控件创建完、模态循环开始前，向**同一个全屏 dialog**增加仓库背景、虚拟列表/分页控件、数量文字和按钮。视觉上两个面板并列，事件属于同一个模态域。
- 不在构造函数返回后弹仓库；不通过第二个 nested ShowAndRun 阻塞原背包；不在不知 dispatcher 路由时简单 Show 两个窗口。
- 大屏优先并列；宽度不足时重排两个视觉区或采用窄列表，仍同时可见可点。最低可用分辨率需实测，不强行把两个405px面板挤出屏幕。
- `PopupContext` 按 dialog 实例保存 heroId、选择、epoch、控件与映射，生命周期与 modal 严格一致；共享原析构释放 dialog-owned 控件，业务上下文独立 detach，异常/超时/ESC/右键重开均清理。
- 所有新 item ID 在安装前检查不冲突；事件包装先处理仓库 ID 和自定义两击选择。原网络、超时、ESC、右键组合/说明等通道必须保留。未知新点击若落入旧回调可能关窗，因此必须主动消费。

### 4.3 单件移入：两次点击，不是双击手势

1. 左键点击原背包有效格：保存 heroId、index、完整记录、mutationEpoch，画选中标记；不关窗，不写鼠标 held 全局，不删除源。
2. 点击仓库的接收区域：重新验证身份、epoch、槽记录和无原生持物，预分配并准备目标库存；成功后删除源并紧缩原生数组/计数，提交目标；失败回滚，物品仍在来源。
3. ESC/取消/选别格仅清本地待选。移入后清选择并刷新两区；关闭返回取消值，避免外层再按旧 index 拿一次。
4. 原鼠标宝物全局 `0x698AD8/ADC` 非空时禁用仓库转移并提示先结束原拖放；本功能不覆盖它，也不把 msg.flags 的 `0x200` 误当 held。
5. 原 GetKeyState 参数 `0x10/0x11/0x12` 是 Shift/Ctrl/Alt；若保留原组合键功能，要用真实键语义，不沿用旧笔记将 Alt 误写为 Shift 的文字。

### 4.4 显示同步

HD 建窗时把宝物 ID/卷轴 subtype 固化为 DEF 帧。存活窗口内只改英雄数组会出现旧图标/新说明错配。

事务成功后统一更新：64格图标与空格、命中映射、选中态、状态栏、仓库页/滚动范围，再 Draw+Refresh；宿主原五格栏也需在安全时机刷新。右键组合改变背包后原来走返回 -2 重开，需要先 detach 当前仓库上下文，新实例再附加；绝不无条件恢复开窗快照，否则会复活已入库物品。

## 5. 无损转移规则

### 5.1 一键移入仓库

扫描当前英雄64格，确认数组/计数一致与合法记录，先准备 `warehouseAfter` 和 `packAfter` 两份临时结果，所有分配成功后一次提交。有效物品按原槽顺序入库；装备19格不碰；空格不入库。不循环“删一件再分配一件”。准备失败时两侧保持原样。

### 5.2 一键取到背包

- 空位以合法原生数组状态计算，不能只信 GUI 数字或 signed count；不一致时先拒绝并诊断，不猜测可放数量。
- 每成功加入一件后才确认从仓库删除这一件。目标满64立刻停止，剩余库存原样保留。
- 原版 `0x4E3200` 具有 bool/AL 成功返回，但 H3API 包装声明为 void；实际接线必须使用已核成功契约。即使空位足够也可能拒绝特定物品（已见 ID3..6 分支），不能“有空位=必成功”。
- 可跳过被原版拒绝的条目继续其它合法条目，并明确报告取回成功/剩余/失败数；绝不能把未加入的记录从仓库删掉。
- 生产核心以成对临时状态计算并校验后提交；若调用原生函数，确认它的副作用与可回滚字段，不能吞异常后假设物品已成功加入。
- 保持完整8字节记录、计数与两侧多重集守恒，重复宝物按条目区别，卷轴第二字段不丢。

## 6. 游戏本体存读档后置扩展

### 6.1 主方案：原文件前缀 + 仓库块 + 固定footer

```text
[原版完整GM1字节，含HD/SoD_SP已经写入的内容]
[本插件仓库payload：整局156个英雄]
[本插件固定长度footer：版本/边界/校验/前缀绑定]
```

- 保持原前缀逐字节不变。不往原生 gzip 解压负载注入事件记录，不重算原压缩 CRC，不修改原存档版本/英雄结构，不另造正式库存文件。
- 物理追加产生的是“原版存档 + 插件附件”，不是宣称它仍是可供所有标准 gzip 工具解到EOF的纯 gzip。是否被目标原版/HD加载链忽略，必须实测；标准 gzip 工具报 trailing data 不能直接等价于游戏拒绝。
- 当前样本的原 CRC 与标准CRC不符，原因未闭合；后置附件不需要改动或修复这份原校验。也不能因此认定尾随追加不可能。
- `SaveGame(0x4BEB60)` 为 thiscall：this + name + 四flag，原成功返回低字节AL=1，`ret 0x14`；旧H3API void包装不能作为成功判断。
- `LoadGame(0x4BEFF0)` 为 thiscall：ECX=this、栈上3个参数（包括存档名及分支参数），`ret 0x0C`。`param_3==0` 进入读档分支；成功在返回前设EAX=1。完整高层语义由反编译入口和调用点确认；hook时须传递全部3个栈参数，不按点读档按钮或窗口显示判断成功。

### 6.2 文件路径与 hook 策略

优先使用 SaveGame/LoadGame 外层 HiHook 建立操作上下文；原调用只调用一次、在插件吞异常保护之外。原生路径构建会补扩展名、走 GAMES/DATA，HD Folders还会改目录，**禁止只用入口 name 猜最终路径**。

可在已授权操作内用 `0x4D6EB0` 流构造捕获真实 path/mode/流对象，或通过底层流对象的 filename字段取得；记录唯一被本次SaveGame/LoadGame使用的流，排除地图/资源/嵌套辅助流。

- 原版SaveGame内部：打开 → `0x4BE0B0`序列化 → `0x4D6FC0` finalize/close → 返回成功。
- 原版LoadGame内部：打开 → `0x4BCA60`反序列化 → close → 返回成功。
- 优先后置原SaveGame函数，确认成功且对应流关闭后追加；若实际HD链内有更早复制，改在**该保存流close成功之后**做附件写入，但仍不插入原生serializer负载。最终时序需由日志证实，不以hook安装顺序猜测。
- `0x4D6FC0` 本身不保留gzclose错误返回；实现需捕获/核对底层close状态，不能只因外层AL=1就宣称写盘健康。
- 重入使用operation token/深度/线程上下文，不能跨异步路径复用最近文件名。路径缓冲按项目规范堆分配4MiB，不在游戏hook栈上放大数组。

### 6.3 保存流程

1. 为本次操作准备完整156仓库snapshot和可序列化payload；逻辑事务中不允许保存半状态。
2. 调原版保存一次，保留返回值/原异常；失败不追加、不修改当前仓库。
3. 获得该次原操作实际文件，确认已关闭、写盘成功及操作token一致；计算原前缀长度和SHA256。
4. 写payload，flush，最后写footer并flush。只有完整且校验通过的footer代表附件提交；重复后置通知由token幂等防止重复追加。
5. 正常原保存以写模式重建文件，旧尾块自然不残留。若遇未重建的文件，只有本插件尾块可被验证替换；不截断不认识的第三方附件，不不断堆叠旧库存。
6. 追加失败显式报告「原版存档已保存，但仓库保存失败，请重试」，当前内存仓库保持不变。能安全回滚时截到本次追加前长度，否则保留故障证据并标记不完整；不能宣称整档成功。

**双阶段限制**：原版写盘和插件追加不可能仅靠footer获得共同原子性；两者之间断电会留下只有原版部分的档。后置方案不能承诺完全消除该窗口。可选的同文件临时完整副本+原子替换只是提交技术，不是正式sidecar库存，但是否引入由实现评审决定；必须诚实说明对旧档/缺失附件的区分限制。

### 6.4 读档与不串档

1. 调原版读取一次。失败时不应用目标仓库，不把旧库存贴到可能已部分改变的Main；清选择并进入仓库不可操作状态，直到下一次成功载入/建局。
2. 原版成功后，从**实际被读取的同一文件**读取footer和payload。先在临时模型做完整校验，再一次替换当前156库存，不合并旧库存。
3. 明确旧档无仓库块：初始化156空仓库。损坏、截断、未知版本、有标记但不完整的附件不能默认为空后继续覆盖保存；清除上一局可见状态并锁定仓库写入，提示重读/换档/用户明确放弃。
4. 完全缺失附件时无法仅凭原版格式判断“从未使用仓库”还是“上次追加前中断/被无插件重存剥掉”。此限制必须告知，不能宣称无标记必然安全旧档。
5. 新游戏成功后清空156仓库；取消建局/读档界面不能清当前正常局库存。把新局边界接入H3RndNew已有明确ScenarioContext和建档成功段，但不把仓库生命周期绑到真随机开关。
6. 英雄A/B、存档A/B、同地图不同局均独立恢复；关游戏后再启动也不能依赖上次进程指针或user.ini恢复库存。

### 6.5 HD/SoD_SP共存

- HD TournamentSaver在游戏call-site `0x4C6DCE`挂回调（HD RVA `0xE9660`），先调原保存，再`CopyFileA`整份文件（RVA `0xE9975`）。我们的附件在此复制前提交，目录副本自然带库存；必须用实际日志确认源与目标都包含附件，不能仅说“整档复制所以永远安全”。
- HD Folders在`0x4BECE6`路径构造层有hook，故捕获最终打开路径比手工拼名字稳。
- SoD_SP `0x4BE0B0`序列化hook在原调用前扩展原生变长记录，并有恢复路径。用途未闭合，不称它已确认是quickspells/FindMe；不复用其私有marker或占用原生事件记录保存仓库。
- 已知插件内部负载属于原文件前缀，原样保留。未来第三方若也在物理EOF追加，不能只在EOF找我方footer；需版本化附件目录/有边界的后向定位协议，找不到不能全文件魔数乱扫或删别人数据。首版目标环境先确认没有此类冲突。
- 未安装H3RndNew时即使游戏能读取原部分，也看不到仓库；无插件重新保存可能丢掉附件。必须在说明中警告，不保证卸载后重存能保留仓库。

## 7. 候选wire format（v1）

以下是设计格式，不是已发布标准；实现前冻结常量与golden fixture，不直接序列化C++容器/结构padding。

```text
payload:
  magic[8] = "H3WHBLK1"
  for heroId in 0..155:
    heroId:u32
    count:u64
    record[count]: artifactId:i32, subtype:i32

footer（little-endian，固定72B）:
  magic[8] = "H3WHEND1"
  version:u32 = 1
  heroSlots:u32 = 156
  blockOffset:u64              // 原文件前缀长度
  payloadBytes:u64
  prefixSHA256[32]             // 绑定同一原版文件，避免尾块错配
  payloadCRC32:u32
  footerCRC32:u32              // 覆盖footer前68B
```

- 包含全部156英雄，固定升序且每ID恰一条，空库存count=0。容量计数和文件偏移用64位；实际大小须用受检加乘，不信任文件count盲目分配。
- 验证版本、156、准确ID顺序、offset/length/end关系、footer校验、前缀hash、payload校验、物品ID与subtype规则和准确消费到块尾；没有任何校验失败后的部分回填。
- CRC用于意外损坏检查，不是安全签名。prefix hash绑定整份原部分，包括其它插件已有负载；复制/改名不变，原部分被修改则附件失配并报错。
- 不预设小固定物品数量上限。解析资源预算/32位内存能力超出时显式拒读并保护原档，不截断库存；实际安全预算需实现评审。
- 空156仓库payload1880B、footer72B；属于离线候选探针观测，不是已部署格式。

## 9. 实施和验收顺序

1. **存档探针先行**：真实GM1副本原字节不变追加小附件；用户游戏内确认原读档、界面元数据、HD/SoD_SP功能正常。包含空附件、非空、未知尾字节、重复原保存、自动保存和Tournament副本。失败即停，不能先上线转移再研究持久化。
2. **纯核心与codec**：0/1/63/64格、ID0/155/非法156、空英雄、同ID卷轴不同subtype、相同宝物多份、拒绝加入、分配失败、计数矛盾、跨ID、撤销选择；全量多重集守恒。
3. **后置存读档**：真实路径、原失败/close失败/附件失败、两阶段断电fixture、未知版本/截断/损坏、无标记档、不串A/B档、同地图不同局、原生读档失败后隔离旧库存、按156ID整包替换、加载/保存上下文重入；HD目录/自动存档副本附件验证。
4. **同dialog联动UI**：仅完整背包出现仓库；ESC/超时/关闭/组合重开同步消失；新按钮不意外EndDialog；不借已析构指针；小分辨率可见可点；原右键/原按键保留；图标与说明/命中一致。
5. **完整操作**：两击移一件、整包移入、取回至64且余数留库、鼠标held保护、左右英雄切换、解雇/战败后同ID复招、保存关游戏重开恢复。
6. **上线门槛**：BAT全量构建、独立测试、源码/产物hash与文档一致；游戏内验收由用户执行。不可把本轮42项格式探针或静态地址核查称为生产功能通过。
